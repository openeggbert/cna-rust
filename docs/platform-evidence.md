## Windows

The loader is written and the platform gates that previously made a Windows
build impossible are gone: `Library`, `Native::_library` and
`Native::from_library` were all `#[cfg(unix)]`, so the crate could not compile
for Windows at all regardless of whether a loader existed.

Two things are verified rather than asserted, because no Windows Rust target is
installed here:

- The NUL-termination helper is compiled and unit-tested on **every** host,
  including that an interior NUL is refused rather than silently truncating a
  path, and that an unpaired surrogate survives. That is the mistake a Windows
  loader is most likely to make, and it does not need Windows to catch.
- The loader body type-checks on Linux against stubbed OS pieces, which catches
  a wrong signature or a borrow error before a Windows host sees it.

`extern "system"` rather than `extern "C"`: the two differ on 32-bit Windows.
The path is encoded with `OsStrExt::encode_wide` rather than through `str`,
because a lossy conversion would corrupt a path containing an unpaired
surrogate.

## WebAssembly

The previous milestone recorded "no compatible CNA WASM C ABI verified". That
is no longer true and was worth re-measuring: CNA builds a real WebAssembly C
ABI artifact from its `cna_c_api_wasm` target -- an ES module factory beside a
`.wasm` -- and a current one on this host exposes **4,053** `cna_*` names.
Emscripten is installed here.

The blocker is on the Rust side, and it is two things rather than one:

1. **No Rust WebAssembly target is installed.** This host has `std` for
   `x86_64-unknown-linux-gnu` only, and `rustup` is absent, so no wasm target
   can be added. Nothing here can compile Rust to WebAssembly.
2. **The binding's linkage model does not exist under WebAssembly.** `cna-sys`
   declares function-pointer types and the safe crate resolves every symbol at
   runtime through `dlopen`/`LoadLibraryW`. WebAssembly has no such loader: a
   consumer links the C API into its module and calls the symbols directly.

The second is the real work, and it is a scoped design task rather than a
missing dependency. A WebAssembly route needs a static-linkage mode in which
`Native` is populated from `extern "C"` declarations instead of from symbol
lookups. The reviewed slice's declarations already exist and
`tools/native-abi/generate.py` derives them from the canonical headers, so the
declarations are not the hard part; the hard part is a second linkage
architecture that cannot be runtime-qualified on this host.

Recorded status: `WASM_CANONICAL_ABI=AVAILABLE`,
`WASM_RUST_TARGET=NOT_INSTALLED`, `WASM_BINDING_LINKAGE=NOT_IMPLEMENTED`.

## Direct linkage (RUST-PLATFORM-004, 2026-08-31)

The binding now fills its function tables two ways. Which one a build uses is a
Cargo feature; the safe API, the ABI check and the errors are identical.

```text
default = ["dynamic-loading"]   resolve every route through the platform loader
          ["direct-link"]       resolve every route at link time
```

`dynamic-loading` keeps the property that made it the default: the crate
carries **no** link-time dependency on CNA, so a project can build with no
library present and point at one later. `direct-link` is the opposite by
design, and is the prerequisite for any target with no dynamic loader.

### One inventory, two mechanisms

There is no second binding. The same 1,391 reviewed routes, the same tables and
the same safe layer serve both modes; only the expression that fills a field
differs, and it comes from one macro:

```rust
acquire!(source, cna_graphics_device_create, sys::cna_graphics_device_create_fn)
```

The route is named by **identifier**, not by string, and that is what makes
direct mode type-checked. `crates/cna-sys/src/linked.rs` is generated by
`tools/native-abi/generate.py --linked --all-manifest-symbols` from the same
Clang view of the canonical headers the ABI verifier uses, and it declares each
route with its real parameter and return types. Assigning
`sys::linked::cna_graphics_device_create` to that route's `_fn` alias is
therefore a coercion **the compiler checks**: a signature that drifts from the
header fails to compile rather than being transmuted into place and crashing
later. Nothing in either mode goes through `*const c_void` or `transmute`.

`NativeSource` states the difference rather than encoding it in a null: dynamic
mode owns a `Library` whose lifetime keeps the pointers valid, and direct mode
owns nothing, because the symbols are part of the executable and there is
nothing that could be unloaded. No fake `Library` is constructed.

### What the media table cost, and what it revealed

One table could not be filled in direct mode: `MediaApi` stored its 203 routes
as `usize` slots that each call site transmuted back into a type it chose
itself. A linked declaration is a typed function, not an address, so direct
mode had nowhere to put it.

Fixing that exposed something worse. Because those fields had no declared alias,
the `SYMBOL_TYPE_MISMATCH` gate had **nothing to check** and had been skipping
the entire family: 203 routes, silently outside the gate that exists to catch
exactly the mistake an untyped slot invites. They are typed now, the acquisition
count went from 1,184 to 1,387, and all 203 proved correctly paired.

### The gate went blind, and now cannot

Moving every call site from a string name to an identifier broke the verifier's
acquisition regex. It did not fail: it matched nothing, reported **zero**
acquisitions and **zero** mismatches, and read exactly like a pass. That is the
worst failure a gate can have, so the verifier now also asserts a floor under
what the scan finds, and a mutation test covers the unreadable-call-form case.

### Evidence

| Check | Result |
|---|---|
| `cargo test --workspace` (dynamic) | 35 suites, 108 assertions |
| `cargo test --workspace --no-default-features --features direct-link` | 35 suites, 108 assertions -- identical |
| out-of-tree consumer builds in direct mode | PASS |
| CNA resolves at **link** time | `NEEDED=libcna_c_api.so` |
| no dynamic loader is imported | `dlopen`/`dlsym`/`dlclose` absent from the binary |
| a real route executes | renderer, platform, platform name, and a full `GraphicsDevice` create/use/dispose |
| ordinary dynamic mode still works | yes, and remains the default |

`tools/direct-link-consumer/verify.py` performs all of these. It deliberately
checks the executable's own dynamic imports rather than only that it compiled:
a build that quietly kept `dlopen` would pass a compile check and fail on the
platform this mode exists for.

### WebAssembly

The prerequisite is done, and the remaining blocker is now purely the toolchain:

```text
WASM_RUST_TARGET=NOT_AVAILABLE
```

`rustc` here knows seven wasm targets but no wasm standard library is installed,
and there is no `rustup` to add one. Building `cna-rust-sys` for
`wasm32-unknown-unknown` fails with "the `wasm32-unknown-unknown` target may not
be installed". No WebAssembly support is claimed, because none has been
compiled or run. `RUST-PLATFORM-003` stays `BLOCKED_PLATFORM`, but it is no
longer blocked on this binding's architecture.
